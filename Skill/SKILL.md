# 数学建模竞赛全流程求解

内部求解按可复现实验管理，正式论文按“问题特征—建模动机—数学模型—求解方法—结果解释—模型检验”组织。代码、结果与论文必须一一对应，但实验日志、候选淘汰过程和工程复现结构不得直接主导论文叙事。默认采用平衡求解：以可靠基线保证交付，只在核心问题上验证题目定制改进；改进失败时回退基线并如实记录，不为每问强行制造创新。默认连续推进，但始终遵守 Codex 的系统规则、沙箱、权限和用户明确要求。

## 确定工作区

1. 将用户明确指定的目录作为比赛工作区；未指定时使用当前工作目录。
2. 将本 skill 的安装目录视为只读资源目录。禁止把比赛产物写入本 skill 目录。
3. 若工作区缺少标准目录，运行：

   ```text
   python <skill-dir>/scripts/init_workspace.py <workspace>
   ```

4. 初始化脚本只补充缺失文件，不覆盖已有文件。只有用户明确要求时才使用 `--force`。
5. 将赛题放在 `<workspace>/题目/`，附件数据放在 `<workspace>/数据/`，计算产物写入 `<workspace>/求解/`，论文写入 `<workspace>/论文/`。
6. 按以下顺序确定本地算法库：用户指定目录 → `<workspace>/../算法/` → `<workspace>/算法/`。若均不存在，在工作区创建 `算法/` 作为沉淀目标；写入工作区外的算法库前遵守权限要求。

## 加载按需规范

- 开始读题、建模或编码前，完整阅读 [references/solution-workflow.md](references/solution-workflow.md)。
- 开始检索候选方法、设计比较实验或沉淀算法前，完整阅读 [references/research-and-promotion.md](references/research-and-promotion.md)。
- 开始生成或修改论文前，完整阅读 [references/paper-spec.md](references/paper-spec.md)。

## 使用 Codex 能力

- 优先使用当前环境已提供的 PDF、文档和电子表格能力读取相应文件；不可用时再使用本地 Python 库。
- 先检查项目内的 `AGENTS.md`，并遵守适用于比赛工作区的仓库规则。
- 使用当前平台的原生命令。Windows 下用 PowerShell 的 `Select-String` 检查日志；POSIX 下可用 `grep`。
- 检索 Kaggle 时记录竞赛或 Notebook URL、作者、更新时间、许可证与可复现要点；检索论文时优先原始论文、权威期刊、会议或预印本页面，并核验题名、作者、年份和永久链接。
- 不要编造文献、DOI、Kaggle 成绩、数据来源或数值结果。网络不可用、需要登录或赛事禁止外部检索时，明确记录限制，继续使用本地算法库与可验证的基础方法。
- 对长任务发送简短进度更新。只有在缺少关键输入、需要权限、存在高风险动作或用户选择会实质改变结果时才暂停询问。

## 执行流程

### 1. 审计输入

1. 列出 `题目/` 和 `数据/` 中的所有文件，记录格式、大小和更新时间。
2. 全量提取题面，识别背景、问题数量、目标、约束、评价指标和提交要求。
3. 全量审计数据：工作表、行列数、字段、类型、单位、缺失、重复、异常值、多级表头、合并单元格、隐藏工作表和备注行。
4. 将事实、假设和待验证判断分开记录。不得用猜测填补赛题或数据缺口。

### 2. 检索候选方法

1. 检索本地算法库，建立与问题类型、输入结构和评价指标匹配的候选条目。
2. 仅当问题属于数据预测、分类或存在高度匹配的公开数据方案时检索 Kaggle 与公开 Notebook，提取特征工程、验证设计、模型组合和超参数范围；优化、机理、评价和证明类问题优先检索与其数学结构匹配的论文、教材和本地算法。不得直接复制无法确认许可或无法复现的代码。
3. 检索支撑候选方法的原始论文和相关领域研究，确认方法假设、适用边界和标准评价方式。
4. 分别标记候选成熟度 `Baseline / Proven / Frontier` 与创新类型 `复现 / 适配 / 组合 / 题目定制假设`；两者互不替代，较新方法不得自动视为创新。
5. 找出与拟采用路线最接近的论文或公开方案，记录共同点、实质差异与尚未解决的限制；若整条方法链与单一来源高度相似，标为复现或适配，不得包装成原创。
6. 对每个外部候选执行过时性审查，核查更新时间、维护状态、依赖兼容性、后续替代方法、任务匹配、泄漏、复现、许可与安全风险，并给出“保留、仅作基线、现代化重写、淘汰”结论。
7. 写入 `求解/方法调研.md` 和 `求解/候选方法清单.csv`，保留来源、成熟度、创新类型、最近方法、核心差异、许可证、过时审查、复现状态、风险和入选理由。
8. 每问至少保留一个可解释参照；对于预测、分类和需要比较的启发式优化，通常再选择 1–2 个 `Proven`，有合适方法且预算允许时可加入一个 `Frontier`。严格解析、枚举、证明或题面已唯一指定模型时，不为满足形式强行增加无意义基线，但须说明模型选择依据。不得按来源热度或发布时间直接决定最终方法。

### 3. 生成求解计划

写入 `求解/求解计划.md`，至少包含：题目总体方向、逐问输入与输出、候选来源与过时审查、适用的比较协议、稳定参照验收条件、核心创新问题、创新预算与预声明成功标准、评价与验证方案、问题间依赖、文件清单和失败回退。仅在确有可复用方法时设置算法沉淀目标。

同时建立 `求解/论文论证蓝图.md`。每问至少填写：题目任务、核心难点、建模动机、决策或状态变量、参数与单位、目标函数或学习目标、约束或假设、模型性质、求解原理、算法输入输出与停止条件、关键结果、结果解释、验证方式和结论边界。蓝图不是论文正文，而是防止代码流程代替数学论证的写作合同；模型与正式结果尚未确定时允许标注待验证，写作前必须补全。

计划完成后直接进入实现；若后续证据推翻计划，更新计划并说明原因。

### 4. 验证稳定基线

1. 为每问创建 `求解/问题X/`，其中包含中文命名的 Python 脚本、`图片/` 和 `结果/`。
2. 把候选实现放入 `求解/问题X/候选方法/`；统一数据预处理、切分、评价指标、随机种子和计算预算。
3. 先运行 `Baseline` 验证数据链路，再运行足以建立可靠参照的 `Proven`。把失败、依赖缺失和不适配原因写入实验记录，禁止只保留胜者。
4. 输出初版 `结果/模型比较.csv` 和 `结果/模型比较.md`；只有数据链路、验证协议、指标和结果均可信时，才进入创新阶段。

### 5. 设计并验证创新

1. 根据真实基线误差、题目约束、问题依赖和最近方法限制，定位 1–3 个核心瓶颈；不要从“模型是否高级”反推创新。
2. 围绕核心问题生成 3–5 个可证伪假设，通常从问题定义、物理或机理融合、数据表示、目标与约束、模型组合、跨问题耦合、不确定性和鲁棒性中选择；筛选 1–2 个进入实验。
3. 将假设、最近方法、核心差异、作用机制、最小实现、比较对象、消融项、主要指标、成功标准、失败条件、预算和状态写入 `求解/创新实验矩阵.csv`。
4. 使用与稳定基线相同的数据、切分、指标、随机种子集合和可比预算，比较稳定基线、成熟强方法、借鉴的前沿方法、题目定制创新和必要消融。
5. 只有当创新收益超过观察到的实验波动，或在预声明的鲁棒性、解释性、成本、约束满足等维度产生可验证收益且主要指标未超过容忍退化时，才判定通过。
6. 创新失败时记录反证与原因并回退稳定方案；若预算允许且失败提供了新信息，默认最多再迭代一轮。没有合格创新时仍完成赛题，但不得在论文中包装创新。
7. 写入 `求解/创新性审查报告.md`，逐项给出“已验证、部分验证、未验证、失败”结论及证据路径。

### 6. 完成逐问求解

1. 依据统一实验选择每问最终方法；创新通过时可采用创新或混合方案，未通过时使用稳定方案。若指标接近噪声水平，优先选择更稳定、可解释和易复现的方法。
2. 更新 `结果/模型比较.csv` 和 `结果/模型比较.md`，同时比较主要指标、波动、运行时间、复杂度、可解释性、约束满足、维护风险和创新消融。
3. 按“先算后画”组织最终脚本：加载与清洗 → 建模与求解 → 输出关键统计量 → 保存表格 → 生成图形。
4. 为每问选择真正有解释力的图，不机械凑图。通常输出 4–6 张；简单问题可少于 4 张，并在计划中说明原因。
5. 在适用时完成误差分析、交叉验证、稳健性或灵敏度分析。交互或协同效应的强结论必须有置信区间、置换检验、留出增益或同等证据，不能只依据单点效应图。
6. 逐个运行脚本，修复异常、空输出、非有限值、字体缺字和路径错误。问题间共享数据写入语义明确的中间文件，不依赖内存中的隐式状态。
7. 每个主要结果段按“数值—现象—原因—意义”组织：先报告结果，再描述跨数据或跨情景现象，区分已验证原因与合理推测，最后说明该结果验证了哪项模型设计或回答了哪个题目要求。

### 7. 按需沉淀通用算法

1. 仅当实际使用且通过验证的方法具有明确跨题复用价值、时间预算允许或用户要求沉淀时执行复用性审计；不要让算法库整理挤占正式结果校验、摘要打磨和论文验收时间。不要沉淀失败候选、纯赛题脚本或许可证不明代码。
2. 去除固定数据路径、赛题字段名、论文绘图和一次性业务逻辑，把数据接口、参数和随机种子显式化。
3. 在本地算法库对应分类下创建独立算法包，至少包含实现、最小示例、测试和 `metadata.json`；记录来源、许可证、候选层级、创新类型、最近方法与差异、消融证据、过时审查、维护状态、适用场景、依赖、验证指标和来源工作区。
4. 运行最小示例和测试。通过后再运行：

   ```text
   python <skill-dir>/scripts/update_algorithm_index.py <algorithm-library>
   ```

5. 执行沉淀时在 `求解/算法沉淀报告.md` 中记录新增、更新、拒绝沉淀的条目及理由；未执行时只需在求解计划中说明“不适用、预算不足或赛后处理”，不把该报告作为交稿阻断项。

### 8. 撰写论文

1. 以 `论文/` 模板为起点，根据实际问题数量增删问题章节。
2. 写作前核对 `求解/论文论证蓝图.md`。每问优先采用“本问分析与建模动机—变量与参数—目标函数—约束或假设—模型性质—求解原理与步骤—结果与解释—本问小结”的语义结构；题型不适用时合并或替换标题，不机械套用。
3. 摘要逐问用清晰分句交代任务、模型、算法、关键定量结果和结论边界。完成后建立逐句功能标注，删除一词多义、空泛评价、过长并列句和无数据支撑的结论。
4. 每个核心算法在正文中说明输入、输出、初始状态、更新规则、可行性保持或修复、停止条件与输出映射。复杂多阶段算法至少提供编号步骤、紧凑伪代码或能说明数学关系的流程图之一；代码附录不能替代正文原理说明。
5. 只写有代码、数据或可靠来源支持的结果。公式、符号、单位、表格与程序保持一致；公式服务于模型定义与推导，不按数量拆分恒等变换。
6. 所有图表在正文中引用；图题、表题、坐标轴和图例使用中文。结果分析遵循“数值—现象—原因—意义”，将推测写成推测。
7. 参考文献必须与正文引用一一对应，并核验作者、题名、年份和来源。
8. 只把 `创新性审查报告.md` 中“已验证”的项目写成创新点；“部分验证”必须缩小表述，“未验证”或“失败”只能作为限制或后续方向。
9. 对每项创新说明最近方法、核心差异和对应消融证据。模板与题目冲突时，以赛题提交要求和证据表达为准，并保持版式一致。

### 9. 编译与视觉验收

1. 在 `论文/` 中运行两遍 `xelatex -interaction=nonstopmode 论文.tex`。
2. 检查非零退出码和日志中的 Error、Overfull、Underfull、缺字及大浮动体警告。
3. 渲染最终 PDF 为页面图像并逐页检查：摘要页数、目录、公式、表格越界、图片裁切、乱码、空白页、孤行和引用编号。
4. 在版面验收之外执行“五分钟评委盲审”：只看摘要、目录、各问首段、主要模型、图表和结论，应能复述每问任务、建模动机、变量、目标、约束、算法原理、关键结果及结论边界。任何核心信息无法定位时，返回对应章节修改。
5. 修改后重新编译并复查，直到无阻断错误；对于无法合理消除的轻微 warning，记录位置和影响。
6. 最终交付 `论文/论文.pdf`、求解计划、代码、关键结果表和必要图件，并简述模型、核心数值、验证结果和剩余限制。内部历史日志、候选池和工程环境说明仅在赛题要求或支撑结论所必需时提交。

## 完成标准

- 题面和数据已全量读取，未遗漏附件或工作表。
- 每个问题都有可运行代码、可追溯结果和适当验证。
- 与题型匹配的论文、公开方案和本地算法检索记录可核查；需要比较的候选方法在统一协议下完成比较，不适用基线竞赛的严格模型有清晰选择依据。
- 每个外部候选均有层级和过时审查结论；旧方法未因年份被机械淘汰，新方法未因发布时间获得无证据优先级。
- 稳定基线在进入创新阶段前已通过验收；核心问题已有创新实验矩阵、必要消融和明确的通过或回退结论。
- 候选成熟度与创新类型分开记录；借鉴的新方法未被自动包装为原创，论文创新主张与审查报告和实验路径一致。
- 若执行算法沉淀，所有写入公共算法库的条目均通过最小示例、测试、许可和复用性检查；未执行时已说明原因。
- 论文中的数值、图表、符号和参考文献与产物一致。
- 摘要已通过逐句功能审查，每问包含任务、模型、算法、关键定量结果和必要的结论边界。
- 每问可明确定位决策或状态变量、目标函数或学习目标、约束或假设，以及输出如何回答题目。
- 每个核心算法已说明原理、输入输出、关键步骤、可行性处理和停止条件；论文无需查看源代码即可理解求解逻辑。
- 主要结果段已区分数值、现象、已验证原因、合理推测和建模意义。
- 已通过五分钟评委盲审，摘要和各问关键页面能够快速传达全文主线。
- PDF 成功编译并经过逐页视觉检查。
- 未隐藏失败、虚构结果或把示例占位符留在最终稿中。
