# 方法检索、实验比较与算法沉淀

## 1. 建立检索问题

先从题面和数据提炼每问的检索画像：问题类型、预测或决策目标、数据模态、样本规模、时间或空间结构、约束、主要指标、可解释性要求和计算预算。分别生成中文与英文关键词。

把检索过程写入 `求解/方法调研.md`，包含检索日期、平台、检索词、筛选规则和访问限制。不要把搜索摘要当作已核验事实。

## 2. 检索本地算法库

递归读取算法库中的 `算法索引.md`、`metadata.json`、实现和测试。按问题类型、输入结构、依赖、指标和验证状态筛选。优先复用已测试的实现，但重新在当前赛题数据上验证，不继承历史成绩。

若条目缺少来源、许可证或测试，将其标为“仅供参考”，不得直接晋升为主方法。

## 3. 检索 Kaggle

搜索相关 Kaggle competitions、datasets 和公开 notebooks。优先选择与当前任务的目标变量、数据结构和评价指标接近的内容。每个候选记录：

- 标题、作者、URL、更新时间和对象类型；
- 竞赛任务、数据特征、评价指标和公开成绩的语境；
- 特征工程、模型、验证切分、集成方式和关键参数；
- 代码许可证、外部数据依赖、运行环境和可复现性；
- 数据泄漏、目标编码泄漏、时间穿越、过拟合排行榜等风险；
- 可迁移部分和不可迁移部分。

Kaggle 成绩只能用于理解原场景，不能作为当前赛题的模型证据。只有在许可证允许且保留来源说明时才能改写代码；否则只借鉴方法思想并独立实现。

## 4. 检索论文

优先查找原始方法论文、同行评审论文、权威会议、官方预印本和领域综述。核验题名、作者、年份、期刊或会议、DOI/arXiv/出版社链接。阅读摘要、方法、实验设置和限制；关键公式或适用性判断不能只依赖二手摘要。

把论文证据分成：方法原理、适用假设、标准指标、已知限制和与本题的迁移理由。论文进入最终参考文献前必须在正文实际引用。

## 5. 候选分层

根据候选在当前实验中的角色标记层级；层级不代表质量排序，也不得以“更新”替代实验验证：

- `Baseline`：简单、稳定、容易复现，用于验证数据链路和建立性能下限；经典方法可以长期保留在本层。
- `Proven`：在相似数据结构和评价指标下有可靠证据、实现可复现且依赖仍受支持的成熟方法。
- `Frontier`：近期论文、新架构或新训练策略，可能提高上限，但证据、稳定性或复现成本仍需验证。

每问至少保留一个 `Baseline`，通常选择 1–2 个 `Proven`；存在任务匹配且预算允许时再加入一个 `Frontier`。没有合适前沿方法时不要强行凑数，`Frontier` 也不得因发布时间较新而自动晋升为主方法。

## 6. 过时性审查

对所有外部候选执行过时性审查，旧方法不得仅因年份较早被淘汰，新方法也不得免审。至少核查：

- 首次发表或发布年份、最近更新时间，以及代码和核心依赖是否仍受支持；
- 是否存在后续修订、官方替代方案或在相似任务上更强且可复现的方法；
- 原任务的数据模态、规模、切分和指标是否仍与当前问题匹配；
- 是否依赖已弃用 API、无法安全安装的版本、不可获得的外部数据或不可接受的计算资源；
- 是否有已知的数据泄漏、排行榜过拟合、复现失败、许可证变化或安全风险；
- 方法的有效思想能否用当前维护的依赖独立实现，而不复制受限或陈旧代码。

网络和时间允许时，至少使用一个较新的原始论文、官方文档或维护者发布记录核验替代关系；不要只依据搜索摘要或发布日期判断。为每个候选给出以下结论之一：

- `保留`：实现仍可维护，适用性证据充分，进入公平实验；
- `仅作基线`：方法仍有参照价值，但不应代表当前性能上限；
- `现代化重写`：保留方法思想，使用受支持依赖独立实现后再实验；
- `淘汰`：存在不可修复的泄漏、许可、复现、兼容性、安全或任务错配问题。

将审查证据、潜在替代方法和结论写入候选清单。只要当前统一实验仍有优势且实现可维护，经典方法可以成为主方法；反之，较新的方法也可以因不稳定或不适配被淘汰。

## 7. 形成候选清单

写入 `求解/候选方法清单.csv`，至少包含：

```text
问题,候选ID,方法名称,候选层级,来源类型,来源URL,首次发布,最近更新,许可证,维护状态,本地条目,关键思路,适用理由,主要风险,替代方法,过时审查结论,审查证据,复现状态,入选状态
```

每问至少包含一个简单基线。通常再选择 2–4 个差异明确的候选；数据或计算预算有限时减少数量并解释。不要用多个几乎相同的超参数配置冒充不同方法。

## 8. 设计公平比较

对同一问题固定：

- 同一原始数据版本与预处理边界；
- 同一训练/验证/测试切分或交叉验证折；
- 同一主要指标及方向；
- 同一随机种子集合；
- 可比的调参预算、超参数搜索范围和停止条件；
- 相同硬件条件或记录归一化后的运行时间。

预处理可作为候选的一部分时，必须使用 pipeline 避免验证信息泄漏。时间序列按时间切分，分组数据按实体分组，空间数据考虑空间阻塞。测试集只用于最终一次评估。

先运行基线验证数据链路，再运行候选。每次实验记录代码版本、依赖、参数、随机种子、开始结束时间、退出状态、指标和产物路径。失败实验保留错误摘要和处置结论。

## 9. 输出比较结果

为每问生成：

```text
求解/问题X/结果/模型比较.csv
求解/问题X/结果/模型比较.md
```

至少比较主要指标、次要指标、均值与波动、运行时间、内存或复杂度、可解释性、约束满足和失败率。主要指标优先；差异接近噪声水平时，选择更稳定、简单、可解释和可部署的方法。

不得删除表现差或失败的候选记录。论文可以精简呈现，但求解产物必须保留完整比较证据。

## 10. 通用化审计

只有同时满足以下条件才沉淀到公共算法库：

1. 在当前任务中实际运行并通过测试；
2. 解决的是可复用算法问题，而不是赛题专属业务流程；
3. 输入、输出、参数、随机种子和错误条件明确；
4. 不包含比赛数据、隐私数据、固定绝对路径、字段硬编码或论文专属绘图；
5. 来源和许可证允许保留或改写；独立实现也要记录思想来源；
6. 至少有一个小型合成示例和自动测试；
7. 与库中已有算法相比具有新增价值，或是经过验证的修复和改进。

不满足条件时，在 `求解/算法沉淀报告.md` 记录拒绝原因，不要为了完成流程强行入库。

## 11. 算法包结构

按类别写入算法库：

```text
算法/<分类>/<算法名>/
├── 算法实现.py
├── 最小示例.py
├── 测试.py
└── metadata.json
```

`metadata.json` 使用 UTF-8，至少包含：

```json
{
  "name": "算法名称",
  "category": "预测",
  "problem_types": ["时间序列预测"],
  "entrypoint": "算法实现.py",
  "dependencies": ["numpy", "pandas"],
  "source_urls": ["https://example.org/source"],
  "license": "独立实现；思想来源见 source_urls",
  "candidate_tier": "Proven",
  "freshness_reviewed_at": "YYYY-MM-DD",
  "maintenance_status": "maintained",
  "known_replacements": [],
  "validated_metrics": {"MAE": 0.0},
  "validated_at": "YYYY-MM-DD",
  "promoted_from": "比赛工作区/求解/问题X"
}
```

指标值必须来自实际测试，不可保留示例数值。若上游许可证不允许再分发代码，不要复制代码；独立实现并准确说明来源与许可边界。

## 12. 入库验收

运行算法包的最小示例和测试，确认在干净进程中可执行。随后运行 `scripts/update_algorithm_index.py` 生成 `算法索引.md`。最后在沉淀报告中记录：新增或更新路径、测试命令、测试结果、来源与许可证、相对基线的证据、已知限制和未沉淀候选。
